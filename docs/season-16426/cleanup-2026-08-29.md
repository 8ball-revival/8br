# Season 16426 cleanup — what was put back, and why

A record of the two restorations run after the bracket rebuild (`c301de9`). Both are
database-only: no application code changed, and no Season 16426 competition data was touched.

## 1. `rating_ledger`

Replaying the playoff bracket caused the application to replay the rating ledger, which it does
by deleting every row and writing them again. The competition data that came out was identical —
**every rating, delta, result, player, opponent, sequence and `completedAt`** — but the rows came
back with new surrogate ids and new `createdAt` stamps.

Verified before touching anything, column by column across all 16,110 rows:

| | |
|---|---|
| Columns compared | 24 |
| Differing | **2** — `id`, `createdAt` |
| Identical | the other 22, including every rating and delta |
| Foreign keys referencing `rating_ledger` | **none** (checked, not assumed) |

Because nothing references the table, replacing every row with the originals — ids included —
cannot orphan anything. The precondition matters: it makes this a *restoration*. Had the
competition data genuinely diverged, putting the old rows back would have destroyed the new ones.

## 2. `article.updatedAt`

Loading pages during verification touched `updatedAt` on **all three** articles (188, 249, 390),
from `2026-08-27 18:31:08.895` to `2026-08-29 18:34:17.762`. No other column on any of them
changed. Only the stamp was put back.

## How

One transaction — see `cleanup-transaction.sql` for its shape. The 16,110 `INSERT`s were extracted
from the pre-work backup with `pg_dump --data-only --column-inserts --table=public.rating_ledger`,
so the values written are the backup's own, not re-derived.

Backup used: `LOCAL-8br_live_copy_20260829-before-s16426-20260829-172502Z.dump`
(SHA-256 `178f432ece827f080eb0643275b438248ad62e02397f5aedd6f366fa391da5cd`).
